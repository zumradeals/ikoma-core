# S0.2 — Qualification expérimentale autorisée : libxml2 et gosu

**Statut : essai isolé, non déployable, sans changement du runtime officiel IKOMA ACCESS.**
Référence `main` : `83fd2f550f7f9aaba95fcea6195e6b1f426081c4`, après R06.
Autorisation : qualification expérimentale d'une variante officielle et analyse ponctuelle d'atteignabilité sur le binaire exact. **Aucune fusion, aucune installation réelle, aucune migration de client ni acceptation de risque.**

## Séparation des deux décisions

### C1 — libxml2 / CVE-2026-6653

Source : [Debian Security Tracker](https://security-tracker.debian.org/tracker/CVE-2026-6653). Trixie conserve une version contenant la base `really2.9.14`, vulnérable. La version Alpine 3.24 de `libxml2` est `2.13.9-r2` à la consultation et se situe au-delà de la plage affectée (jusqu'à 2.11.0).

Candidat strictement expérimental : `php:8.5.12-fpm-alpine3.24` et `postgres:18.6-alpine3.24`, images officielles de même branche majeure. **L'image PHP candidate n'est qu'un runtime de test** : elle ne copie ni code IKOMA ni vendor/ressources et ne constitue donc pas l'image de production intégrée.

Le fichier `docker/qualification/php-alpine.Dockerfile` installe les mêmes familles d'extensions PHP que l'image actuelle, avec les dépendances nécessaires propres à Alpine. La sonde `scripts/security/qualify-alpine.php` exige libxml2 compilée et chargée >= 2.11, valide les extensions et un parcours fictif CSV, XML, ZIP, GD. La qualification PostgreSQL démarre une instance 18.6 **sans réseau**, temporaire, construit une table fictive, teste SQL et une sauvegarde/restauration. Les ID d'images, versions, renseignements système et rapports Trivy résumés sont archivés.

Trivy analyse les deux images candidates de toutes gravités et conserve les nouvelles CVE éventuelles ; la suppression de **CVE-2026-6653** doit être démontrée sur les deux. **Ce test n'établit pas la compatibilité complète de Laravel, OpenSpout, des locales/collations, de toutes les permissions, de l'installation ni du déploiement**. Un rapport Trivy favorable ne constitue pas une autorisation de basculer de Debian vers Alpine.

Garde-fous avant toute éventuelle adoption :
- image complète PHP IKOMA et toutes les commandes de son entrée/provisionnement sur Alpine ;
- migrations de recette, rôles, import XLSX réel par OpenSpout, badge, audit, synchronisation, E2E ;
- évaluation de `glibc` contre `musl`, locales/collations SQL, index `unaccent`, sauvegarde/restauration et continuité ;
- inventaire comparé de **toutes** les CVE, y compris les nouvelles ; diagnostic séparé de chaque critique ;
- décision architecturale explicite, maintenance/support éditeur et plan de retour arrière ; jamais de migration directe d'un volume PostgreSQL existant.

### C2 — gosu / CVE-2025-68121 / GO-2026-4337

Source : [avis officiel Go](https://pkg.go.dev/vuln/GO-2026-4337) ; recommandation du mainteneur : [gosu 1.19 SECURITY.md](https://github.com/tianon/gosu/blob/1.19/SECURITY.md).

Le workflow extrait `/usr/local/bin/gosu` de `postgres:18.6-trixie`. **Il refuse d'analyser un autre binaire** que celui mesuré en R04 : SHA-256 `52c8749d0142edd234e9d6bd5237dff2d81e71f43537e2f4f66f75dd4b243dd0`. Le SHA du conteneur est également consigné. Le binaire n'est pas joint aux preuves publiées.

Une installation ponctuelle en runner de `govulncheck v1.1.4` (version officielle employée par le projet gosu) réalise une analyse **binaire et au niveau des symboles**, puis un script refuse tout rapport absent ou incomplet. L'avis officiel `GO-2026-4337.json` est consulté et empreinté ; aucun `GO-2023-1840` ou autre avis n'est masqué dans le rapport.

**Critère de constat préliminaire** : aucun symbole vulnérable de la CVE n'est signalé sur le binaire identifié. **Ce constat ne vaut pas acceptation automatique** : il doit être relu, rapproché du parcours réel de démarrage et contresigné. S'il manque des symboles, si l'outil échoue, si le binaire diffère ou si le résultat est incertain : **STOP, CVE maintenue bloquante**.

La CI Trivy d'IKOMA continue de signaler ce qu'elle détecte. Une éventuelle exception spécifique à ce digest nécessitera une décision séparée avec durée de validité, contrôle d'intégrité, responsabilité et surveillance ; aucune liste d'ignorance n'est ajoutée par l'expérience.

## Résultat attendu, sortie et limites

Les deux jobs produisent des **preuves**, pas un composant livrable. Leurs résultats doivent distinguer : absence de la CVE recherchée dans un candidat, absence de symboles vulnérables dans le binaire exact, résultat insuffisant/inconnu, et autres vulnérabilités éventuellement révélées. Aucune conclusion globale « sécurisé à 100 % ».

Les contrôles de livraison déjà en place ne changent pas, les deux CVE restent ouvertes dans S0.1 tant qu'une décision formelle n'a pas validé des artefacts corrigés ou une non-applicabilité prouvée.

**Interdit :** fusion automatique de la branche expérimentale, déploiement, manipulation de données client, migration d'une base exploitée, désactivation Trivy, correction qui mélange les distributions, changement fonctionnel F01–F09.
