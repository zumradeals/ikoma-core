## Contrat de correction

1. La CLI doit être appelée avec `gh attestation verify "oci://<image>@sha256:<digest>" -R zumradeals/ikoma-core --format json`, et avec une contrainte explicite sur le commit et la branche source. **Échec bloquant si signature invalide ou résultat JSON vide.**
2. Le vérificateur `scripts/security/s06-attestation-gate.py` accepte seulement une liste non vide de résultats cryptographiquement vérifiés contenant un sujet `ghcr.io/zumradeals/ikoma-access-postgres-candidate` dont `digest.sha256` égale **exactement** celui du manifeste GHCR, avec prédicat SLSA v1. Le rapport publié demeure synthétique, sans sérialiser les certificats ou clés.
3. Le workflow de reprise `qualification-s06-verify-existing.yml` fonctionne **uniquement par déclenchement manuel sur `main`** : il vérifie le run GitHub original, récupère **son** artefact `release.json`, vérifie l'image par digest, l'attestation GitHub, puis rescane strictement l'image chargée sur runner indépendant.
4. Le même workflow applique `s06-oci-gate.py consumer`, puis démarre PostgreSQL sur volume temporaire neuf et vérifie les 4 000 enregistrements relationnels fictifs. Aucun contournement Trivy.
5. Il est interdit de republier l'image déjà existante pour « corriger » un simple échec de lecture, de réécrire le tag `rc-<commit>`, d'utiliser `latest`, ou d'affirmer qu'un digest de configuration Docker est un digest de manifeste OCI.
6. Le workflow S0.6 d'origine utilise désormais `--format json` et le même gardien pour toute publication candidate **future** ; cela ne modifie pas l'image existante.
