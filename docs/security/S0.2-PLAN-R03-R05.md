# S0.2 — Plan R03–R05 soumis à validation, non exécuté

La première phase autorisée s'arrête à R01–R02. **Aucune action ci-dessous n'est lancée**, aucun correctif n'est implicitement autorisé par une CI rouge. La référence historique reste S0.1 et ses preuves ; les candidats devront être réévalués à la date d'exécution.

## R03 — Bibliothèques OS runtime, libxml2 en priorité

1. Partir des trois IDs/digests exacts et des JSON finaux produits par R02 ; séparer paquets runtime, outils auxiliaires et en-têtes. Comparer les avis Debian/amont aux versions installées, sans comparer naïvement le préfixe de `really2.9.14`.
2. Vérifier les mises à jour de sécurité disponibles dans les variantes officielles compatibles. Ne pas mélanger stable/sid, ne pas changer de distribution ou de version majeure sans décision explicite. Si aucun correctif compatible n'est disponible, présenter les options et leurs impacts avant toute modification.
3. Pour libxml2, examiner le chemin XLSX/OpenSpout, les paramètres de parsing et les autres consommateurs dans PHP/PostgreSQL. Les refus DOCTYPE/ENTITY existants ne constituent pas une preuve générale de non-exploitabilité.
4. Appliquer une modification minimale des composants autorisés dans un lot isolé ; reconstruire les images finales et conserver le nouveau lien source/digests. Aucun `.trivyignore` global, aucune suppression d'alerte pour absence de correctif.
5. Vérifier extensions PHP, GD/JPEG, ZIP/XML, import CSV/XLSX valide, refus d'entrées adverses dans une recette isolée et tests applicatifs concernés. Refaire R02 sur les images exactes et comparer les alertes avant/après.

Clôture : correctif livré prouvé par version et avis officiel, régressions appropriées absentes, rapport final vérifiable. Toute vulnérabilité résiduelle garde un état explicite soumis au dirigeant, sans risque accepté par défaut.

## R04 — PostgreSQL et Go intégré à gosu

1. Identifier le digest final PostgreSQL et le binaire gosu ; relever sa version de compilation Go depuis la preuve scanner. Les 26 alertes historiques concernent la bibliothèque intégrée à ce binaire.
2. Vérifier les images officielles compatibles intégrant un gosu reconstruit avec une version Go corrigée ; ne pas présenter la mise à jour du Go de l'hôte comme une correction de gosu.
3. Si nécessaire, qualifier symboles liés et appels atteignables avant un verdict non applicable. Le rôle de changement d'utilisateur ne prouve pas seul l'absence de code TLS exploitable.
4. Proposer le candidat exact (version, variante, digest, avis couverts) et la différence de surface. Privilégier un changement de distribution tiers maintenu sans construction artisanale non approuvée.
5. Après autorisation de ce candidat : démarrage PG sur volume fictif neuf, redémarrage, santé SQL, migrations de recette uniquement, abandon des privilèges, sauvegarde/restauration fictive et compatibilité des trois rôles PHP.

Clôture : nouveau binaire/digest scanné, disparition des alertes corrigées ou justification individuelle documentée, aucune régression des opérations SQL et de restauration. Aucune base réelle utilisée pour valider ce lot.

## R05 — Symfony Mime

1. Confirmer `symfony/mime v7.4.19` dans le verrou et l'avis `CVE-2026-45070 / GHSA-vqc8-7275-q272`. Le correctif S0.1 est 7.4.22 sur la branche 7.4 ; revérifier les versions officielles lors de l'exécution.
2. Résoudre une mise à jour ciblée compatible avec les contraintes Laravel et les dépendances transitives. Expliquer chaque mouvement du verrou ; aucune mise à jour globale ni changement majeur automatique.
3. Vérifier le rejet des noms de paramètres MIME non valides, les chemins de messages/en-têtes réellement utilisés et les tests applicatifs concernés. Refaire Composer Audit intégral pour conserver les alertes sous le seuil, puis R02 sur le PHP final.
4. Documenter versions avant/après, référence de l'avis, tests exécutés et éventuelles limites. Les anciennes versions annoncées à tort comme corrigées dans l'avis ne sont pas retenues.

Clôture : version compatible corrigée présente dans le vendor final et le verrou, avis Mime absent de l'audit, régressions pertinentes testées. Pas de migration, déploiement ni homologation implicite.

Ordre proposé après validation : figer les preuves R02, puis R03/R04/R05 en changements distincts ; R05 peut avancer indépendamment dès que sa résolution ciblée est approuvée. R06–R11 restent hors de cette phase. Le gel des nouvelles mises en service commerciales avec données réelles est maintenu jusqu'à une décision officielle fondée sur les preuves.
