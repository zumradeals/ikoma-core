# IKOMA ACCESS — S0.3 / candidat PHP Alpine uniquement

**Statut : qualification technique en PR, non livrable avant validation de la sécurité.**  
Base de départ : `main` `1cb59cde719d7cc29b16914826b35117881d3514` (PR #49 fusionnée).

## 1. Vision — réduire les vulnérabilités sans déplacer les données

Les scans Trivy sur Debian détectent 125 occurrences HIGH/CRITICAL dans l'image PHP de développement et 88 dans l'image PostgreSQL ; Nginx : zéro. `CVE-2026-6653` touche libxml2 sur Debian Trixie. Le suivi Debian indique que la version Trixie reste vulnérable, sans correctif empaqueté disponible au moment de ce lot. Une réinstallation d'un paquet Trixie identique ne constitue pas un correctif.

La recette intégrée S0.2 précédente (#48) avait établi 0 HIGH/CRITICAL sur une image PHP Alpine 3.24 **de production**, tout en conservant 26 alertes Go sur PostgreSQL Alpine. Depuis, la qualification #49 a validé l'ordre portable, les E2E Alpine et la compatibilité fonctionnelle. Ces preuves justifient **un candidat PHP distinct**, pas une déclaration de sécurité absolue.

## 2. Conception — invariants contractuels

- Seule la base PHP **développement et production** passe à la distribution déjà qualifiée `php:8.5.12-fpm-alpine3.24`, avec `apk upgrade`, extensions identiques et suppression des dépendances de compilation.
- **PostgreSQL reste `postgres:18.6-trixie`**, mêmes volumes, même version, mêmes données, même protocole ; Nginx inchangé.
- Le worker PHP de développement reste sans privilèges et dispose uniquement de l'appartenance au groupe 33 pour lire le `.env` local (mode `0640`). Aucune ouverture de permission générale.
- Le processus de production reste UID 10001, fichiers applicatifs non modifiables, services internes et secrets inchangés.
- Les blocages Trivy restent inchangés pour le dépôt entier : toute HIGH/CRITICAL du serveur PostgreSQL demeure visible et bloquante.
- Aucune adoption Alpine de PostgreSQL, aucune migration de base de données, aucune modification d'une instance ni déploiement.
- La distribution PHP candidate n'est pas un simple renommage d'image : le verdict dépend de la version réellement construite et scannée dans la CI.

## 3. Implémentation proposée

- `docker/php/Dockerfile` : base Alpine de développement, bibliothèques et extensions PHP compatibles, lecture groupe 33 au worker.
- `docker/prod/Dockerfile` : base PHP Alpine, dépendances de compilation retirées, utilisateur `ikoma` UID 10001 conservé.
- Nouveau contrôle `qualification-php-alpine.yml` : construction effective de l'image PHP finale, vérification des extensions, import CSV/XLSX et scan Trivy de cette **image précise**, sans ignore-file et sans abaisser le seuil.
- Les recettes existantes de `Fondations L0` restent la preuve de bon fonctionnement PHP/frontend/E2E et de production restaurable.

## 4. Critères de décision

**GO technique PHP uniquement** après :
1. construction reproductible de PHP développement/production et réussite des recettes de l'application ;
2. scan Trivy PHP final complet : aucun HIGH/CRITICAL, ou à défaut inventaire des nouveaux risques et STOP de ce lot ;
3. aucune régression d'authentification, imports CSV/XLSX, badges, E2E, sécurité, restauration ;
4. attestation que la base PostgreSQL et ses volumes ne sont **pas modifiés**.

**STOP de mise en production** tant que PostgreSQL Debian conserve ses vulnérabilités bloquantes ou que les preuves de la CI finale sont incomplètes. Les 26 alertes Go du candidat PostgreSQL Alpine exigent un traitement **distinct** (correctifs de la chaîne Go ou avis documentés et décision de risque).

## 5. Retour arrière

Un revert Git des changements de Dockerfile restaure les images PHP précédentes, sous réserve d'une validation sur l'environnement cible. Aucune conversion de base n'est prévue par ce lot. Pour une instance réellement déployée, la sauvegarde/restauration et la cohérence des migrations sont des procédures séparées : un simple revert Git ne remet pas les données en arrière.
