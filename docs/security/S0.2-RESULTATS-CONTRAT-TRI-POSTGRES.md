## Interprétation et limites

1. Le candidat `COLLATE "C"` rend le **départage explicite et reproductible pour les données fictives testées**. Le laboratoire ne démontre ni l'identité de tous les résultats de `pg_trgm.word_similarity`, ni l'identité de la recherche locale JavaScript pour tous les Unicode, ni la conservation de l'ordre historique Debian.
2. Les scores du test sont prédéfinis pour **isoler le contrat de départage** ; il ne s'agit pas d'un test complet de la formule SQL réelle de `VisitorSearch::searchDetailed`.
3. Le `REINDEX` et la restauration se font **uniquement sur bases éphémères**, sans données réelles ; aucune migration ni reconstruction d'index d'un client n'a été réalisée.
4. Le code actuel de `VisitorSearch.php` et les listes Admin continuent à ordonner par collation implicite. Le banc d'essai propose un choix à ratifier : **standardiser le départage portable** ou **préserver le tri historique Debian** ; les deux objectifs ne sont pas équivalents.
5. La PR #49 reste distincte : son E2E navigateur Alpine a échoué après tests PHP ; l'échec réel ne peut pas être déclaré corrigé par cette preuve. Les 26 vulnérabilités Go (25 HIGH + 1 CRITICAL) restent visibles et non automatiquement acceptées.

## Recommandation d'architecture

**Candidat A — contrat de départage portable :** proposer le tri explicite et immuable avec `COLLATE "C"` et UUID final, sans modifier les scores, l'ordre de priorité VIP ni les droits d'accès. Le risque d'un changement visible de classement des listes sur Debian doit être accepté explicitement avant implémentation, et les recherches locales/offline doivent être comparées sur accents, homonymes, Unicode et scripts non latins.

**Candidat B — conserver le classement historique Debian :** conserver la base et sa sémantique de collation jusqu'à qualification d'un mécanisme de compatibilité de version de collation. La preuve actuelle ne qualifie **aucune** migration de données réelles vers Alpine.

**Décision nécessaire :** choisir A ou B dans un contrat approuvé. Avant adoption d'Alpine pour la base PostgreSQL : traitement de l'échec E2E sur la PR #49, audit métier de tri/recherche sur données de démonstration représentatives, procédure de migration logique sur copie, reconstruction des index, sauvegarde/restauration et validation du rollback, revues sécurité des 26 avis Go.

**Aucun GO de fusion ou d'exploitation commerciale. Gel commercial maintenu.**
