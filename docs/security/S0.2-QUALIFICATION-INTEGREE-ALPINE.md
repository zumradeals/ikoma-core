# S0.2 — Qualification intégrée complète d'IKOMA ACCESS sur Alpine

**État : PR expérimentale, non fusionnable en l'état.** Cette qualification a été autorisée pour éprouver une base alternative après les deux dossiers C1 (libxml2) et C2 (gosu). Elle n'autorise aucune migration de production ni la substitution des images commercialisées.

## Source de vérité et indépendance

Base de référence : `main` `83fd2f550f7f9aaba95fcea6195e6b1f426081c4` (R06 fusionné). Les fichiers existants `docker/prod/Dockerfile` et `docker-compose.prod.yml` **ne sont pas modifiés dans la PR**. La CI crée un **worktree Git isolé**, applique à ses deux copies des transformations strictes et contrôlées, puis crée un commit local éphémère identifié dans `provenance.json`. Ce commit n'est jamais poussé et n'est pas une version livrable. Les transformations proviennent de `scripts/security/prepare-integrated-alpine.py`, lui-même versionné dans Git.

- Le stade `assets` Node et l'image Nginx officielle restent identiques.
- Le cœur PHP **avec tout le code, les dépendances de production, les configurations, scripts et ressources** reste identique au modèle actuel, mais son stade `base` est généré depuis `php:8.5.12-fpm-alpine3.24` avec dépendances `apk` officielles et `apk upgrade --no-cache`. La création du même utilisateur sans privilèges (`10001`) est adaptée à Alpine.
- PostgreSQL conserve sa version majeure 18.6, image `postgres:18.6-alpine3.24` actualisée via `apk upgrade --no-cache` et taguée **localement** `ikoma-qualification-postgres:18.6-alpine3.24`. Les volumes PostgreSQL sont fictifs et ne proviennent d'aucun client.

## Contrat de tests représentatifs

La CI utilise **le véritable `deploy/prod/install.sh`** dans le worktree éphémère avec clés fictives et ports d'essai, sans planification. Elle réutilise ensuite `deploy/prod/ci-recette.sh` pour contrôler l'assistant initial fermé après usage, l'authentification, les en-têtes HTTP de sécurité, les utilisateurs non-root, les migrations, le refus de données de démonstration, la sauvegarde chiffrée, la restauration sur base vierge, l'audit et le retour arrière.

Sont ajoutés : contrôle explicite de F06 désactivé par défaut, capture des locales et extensions PostgreSQL, test des bibliothèques PHP réellement dans l'image finale (CSV et XLSX OpenSpout, libxml, GD/ZIP, Symfony Mime R05), analyse Trivy de **php, db, nginx réellement exécutés**, et analyse `govulncheck` binaire/symboles sur le **gosu effectivement extrait de PostgreSQL Alpine**. Ce dernier point interdit d'étendre sans mesure la conclusion de R04 concernant le binaire Trixie.

Les scans de toutes gravités restent complets, sans seuil assoupli, liste d'ignorance ni verdict de faux positif global. `scripts/security/qualify-integrated-alpine.py` contrôle les identités des trois images, la couverture des paquets, l'absence de `CVE-2026-6653`, l'absence de nouvelle critique hors `CVE-2025-68121` de gosu, et l'absence de symbole atteignable de cette dernière. **Les HIGH restent visibles**, non automatiquement acceptées.

Les rapports publiables se limitent aux données fictives, identités des images, inventaires d'alertes et empreintes. Secrets et journaux d'installation complets restent exclusivement dans le répertoire privé du runner ; aucune donnée réelle n'est copiée.

## Critères de STOP et limites

Toute compilation, migration, import XLSX, sauvegarde/restauration, contrôle d'audit, identité d'image ou analyse de sécurité manquante arrête l'essai. Un résultat « zéro alerte critique applicable » n'est **pas** un résultat « zéro CVE », ni une autorisation de livraison. Une non-applicabilité gosu reste limitée à **l'identité de son binaire**.

**Limites obligatoires à lever avant une décision commerciale :** cette CI ne simule pas toutes les conditions d'exploitation ; comparer l'ordre de tri, les collations `glibc` contre `musl`, les résultats accentués `unaccent`, les index opérationnels et le comportement des bases clientes existantes avec des jeux de données représentatifs ; exécuter les tests métier complets et les E2E sur le candidat Alpine lorsque l'outillage de test est prévu ; examiner les 25 alertes HIGH Go restantes ; documenter l'interruption d'Internet et la continuité du contrôle des accès ; prévoir une migration de données **sur copie** et un rollback opérateur avant tout déploiement.

L'emploi d'Alpine comme nouvelle base durable n'est **pas** décidé par cette PR. Aucune fusion, aucune désactivation de Trivy, aucune autorisation de produire ou d'exploiter des données client réelles. Le gel commercial reste maintenu.
