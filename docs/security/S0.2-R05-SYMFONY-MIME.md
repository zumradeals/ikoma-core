# R05 — Correction ciblée Symfony Mime

Base : `ace54da1a8a93855c7c246b7d1b1a22fcd2a5a8f`. Date : 31 octobre 2026. PR indépendante de R03 et R04, à ne pas fusionner automatiquement.

## Problème et correction

L'audit de référence signale `CVE-2026-45070 / GHSA-vqc8-7275-q272 / PKSA-wtxr-p26d-nn42` dans `symfony/mime v7.4.19`, dépendance transitive de production. L'avis est moyen et figurait dans `ignored-advisories` à cause du seuil Composer existant ; il ne s'agit pas d'une absence de vulnérabilité.

L'[avis officiel Symfony](https://symfony.com/cve-2026-45070), relu le 31 octobre, confirme 7.4.22 comme première version corrigée de la branche 7.4. Les versions précédemment annoncées comme corrigées n'avaient pas reçu le patch. Le [code officiel v7.4.22](https://github.com/symfony/mime/blob/v7.4.22/Header/ParameterizedHeader.php) rejette les noms de paramètres hors de la classe token RFC. Un nom non fiable peut autrement injecter des en-têtes ; aucun chemin d'exploitation IKOMA n'est démontré par cette mise à jour.

La résolution est effectuée par **Composer du projet** : `composer update symfony/mime:7.4.22 --no-install --no-scripts --no-interaction`, avec PHP de l'image de développement existante. Le verrou n'est pas reconstruit à la main. L'exécuteur local ne dispose pas de PHP/Docker ; un workflow de préparation sur runner fictif a généré le verrou, ensuite récupéré par artefact et vérifié par SHA-256. Ce workflow n'est plus présent dans le diff final et n'a modifié aucun contrôle de sécurité existant.

Le run de résolution 41205835080 a réussi. L'essai précédent avait résolu le même paquet mais le validateur strict refusait deux avertissements de contraintes exactes déjà présentes sur bacon/openspout ; aucune contrainte n'a été assouplie. Le validateur standard conserve les erreurs de schéma/verrou comme échecs. L'exécution sous l'UID du runner évite l'exception globale de confiance Git du conteneur. Les scanners et seuils restent inchangés.

## Diff exact du verrou

- Un seul paquet modifié : `symfony/mime v7.4.19 → v7.4.22`.
- Aucun paquet ajouté ou supprimé ; aucun autre paquet direct, transitif ou de développement changé.
- `composer.json` et son `content-hash` sont inchangés, ainsi que les références PHP/PostgreSQL/Nginx et npm.
- Métadonnées générées par le Composer courant : `plugin-api-version 2.6.0 → 2.11.0` ; `stability-flags` et `platform-dev` deviennent des objets JSON vides au lieu de tableaux vides. Ces champs sont conservés tels que générés, sans mise à jour d'un autre paquet ni changement de l'installateur Composer déjà utilisé.

Les références du paquet, empreintes, différences et IDs d'artefact figurent dans [R05-RESOLUTION.json](R05-RESOLUTION.json). Les paquets ont été comparés comme objets complets, pas seulement par numéro de version : tout changement transitive supplémentaire aurait arrêté la préparation.

## Usages et tests de régression

La recherche ciblée dans `app/` ne trouve pas d'appel direct à ParameterizedHeader, addParameterizedHeader, setParameter ou Mail:: ; le composant reste utilisé transitivement par le framework/mail. Les notifications hôte du projet sont des enregistrements applicatifs, pas une preuve d'exploitation MIME. Cette recherche n'est pas un audit complet du code ou de toutes les configurations client.

`tests/Unit/MimeSecurityTest.php` vérifie constructeur, setParameter, setParameters et wrapper Headers sur sept noms invalides : CRLF, espace, séparateurs, guillemet, nom vide et tabulation. L'état valide doit être conservé après rejet. Le test vérifie également les noms valides, un nom de fichier contenant des espaces et un message multipart avec pièce jointe fictive ; aucun courriel n'est envoyé.

La sonde `scripts/security/mime-runtime-probe.php` vérifie aussi le composant **réellement chargé dans l'ID PHP final** : version corrigée dans la branche 7, rejet du nom CRLF et sérialisation valide. Elle s'exécute sans réseau, sans secret, en lecture seule ; aucune requête métier ni envoi de courriel. Son artefact `r05-runtime` distingue cette preuve d'image du seul verrou et des tests du vendor de développement.

La CI complète doit vérifier Pint/Larastan, les tests PHP/frontend/E2E, l'installation production, la sauvegarde/restauration fictive et les trois images finales. Les rapports Composer et Trivy sont comparés à la référence R01–R02 par identifiant/paquet/version, avec les alertes non résolues conservées. Avant analyse de cette CI finale, aucune réussite du nouveau test ni disparition effective d'alerte dans l'image n'est prétendue.

## Résultats attendus et limites

La CVE Mime doit disparaître de l'audit Composer après la résolution et du PHP final si le scanner la détectait. Les HIGH/CRITICAL système ne sont pas corrigées par cette PR : référence 120 occurrences PHP + 88 PostgreSQL, 110 CVE élevées/critiques distinctes, dont trois critiques. La CI peut et doit rester rouge pour ces alertes. Une absence d'avis Mime n'est pas une homologation de sécurité ni une résolution de R03/R04.

Les résultats réels, runs et artefacts sont présentés dans la PR avant toute fusion.
