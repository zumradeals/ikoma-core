# S0.2 — Qualification préalable à l'adoption de la variante Alpine

**Statut : PR de recette, aucun GO d'adoption, aucun GO commercial.**  
Référence de départ : `main` `264af4da6a9b1dd99b7ac455990d686d9b61eb0f`, après fusion de la PR #48 (qualification intégrée réussie).

## Décision autorisée

Éprouver, sans déploiement ni fusion, les trois réserves techniques exprimées dans le rapport S0.2 de la PR #48 :

1. **Les 25 vulnérabilités élevées Go** : établir un inventaire **par identifiant CVE**, version et binaire, comparer chaque CVE du scanner Trivy aux avis Go communiqués par `govulncheck` sur le binaire `gosu` extrait de l'image PostgreSQL Alpine candidate. Les avis non associés ou sans preuve restent *non qualifiés*. Un symbole détecté impose l'arrêt et une revue.
2. **La sémantique PostgreSQL Debian vs Alpine** : sur PostgreSQL 18.6, comparer les versions, locales, encodages, tris, `unaccent`, recherches non accentuées, ordre `pg_trgm` et disponibilité des index sur les **mêmes noms fictifs**. Toute divergence de comportement est documentée et arrête l'acceptation de parité, sans modifier les collations pour faire artificiellement correspondre les sorties.
3. **Les tests métier complets sous Alpine** : construire l'image PHP de développement Alpine et l'image PostgreSQL Alpine dans un **worktree Git temporaire**, utiliser les véritables commandes du projet `make install`, `make up`, `make migrate-fresh-seed`, `make test`, `make e2e` et `make e2e-agent`. Les suites existantes testent les droits, badges, poste d'accueil, accueil multi-zone, contrôles et écran agent suivant leur couverture actuelle.

## Sources, méthodes et contrôle de portée

- CI : `.github/workflows/qualification-adoption-alpine.yml`, trois jobs indépendants.
- SQL fictif : `scripts/security/pg-locale-fixture.sql` ; comparaison : `scripts/security/compare-pg-locales.py`.
- Audit Go : `scripts/security/audit-gosu-highs.py`. Entrées obligatoires : ID de l'image PostgreSQL réellement scannée, rapport Trivy sans fichier d'ignorance, binaire gosu extrait de cette image, version Go et événements de `govulncheck` officiel.
- Laboratoire E2E : `scripts/security/prepare-alpine-e2e.py`, exclusivement en GitHub Actions, refus d'un worktree impur ou contenant une instance préexistante. La mutation des fichiers Docker se fait seulement dans le worktree éphémère et donne lieu à un commit local non poussé, avec SHA d'entrée et empreintes publiables.
- La CI n'installe aucun outil dans la production, ne change ni le `Dockerfile` officiel, ni les `Compose` officiels, ni les politiques Trivy de `main`.
- Aucun fichier de données réelles, secret, mot de passe de test, copie de base client ou journal privé n'est archivé. Les artefacts contiennent les références d'images, les résultats des comparaisons, des CVE, des versions et des indicateurs PASS/STOP.

## Interprétation obligatoire des résultats

**Une CI verte ne suffit pas pour admettre la migration d'un client** :
- `govulncheck` en mode binaire/symbole ne démontre pas que **toute** CVE absente de son flux est inapplicable. L'état `UNMAPPED_NEEDS_MANUAL_REVIEW` reste ouvert. Le constat `NO_VULNERABLE_SYMBOL_REPORTED` est une preuve technique bornée, pas une exemption automatique.
- Une comparaison sur 18 noms et quelques index fictifs n'établit pas l'équivalence de l'ordre de tri et des index d'une base client existante. Les collations `glibc` vs `musl` peuvent diverger même si cette fixture ne le montre pas.
- Les E2E de ce lot utilisent l'image de **développement** PHP sur Alpine avec tout le code métier et les suites existantes. La PR #48 a testé l'image **production** complète Alpine avec installation, imports et restauration. Ensemble, ces essais restent des validations de recette, non une simulation parfaite des conditions d'exploitation.
- Les 25 HIGH et l'unique critique Go détectées précédemment restent visibles dans le dispositif Trivy. Le retour `0` de `govulncheck` ne signifie ni absence de vulnérabilités ni acceptation du risque.

## Critères GO / STOP proposés (non encore ratifiés)

- **GO pour soumettre un dossier de décision d'adoption** : aucune erreur technique dans les trois jobs, aucune divergence inexpliquée de recherche/tri, inventaire exhaustif des CVE et verdict explicite pour chaque avis, tests PHP/E2E réussis, inventaire des risques encore ouverts.
- **STOP** en présence d'une régression fonctionnelle, d'une anomalie de collation, d'une CVE Go avec symboles vulnérables détectés, d'un avis non documenté ou d'une preuve manquante. Une divergence observée n'autorise pas le masquage des alertes.
- Avant toute livraison : qualification des risques résiduels HIGH avec propriétaire et réexamen, procédure de migration restaurable **sur copie de base de données**, vérification de cohérence métier et des index, décision explicite de direction et du responsable sécurité, maintenance des images choisies, gel commercial levé séparément.

**Interdictions maintenues :** aucune fusion de la PR à ce stade, aucun remplacement de Debian en production, aucun déploiement, aucun transfert de données clients, aucune levée du gel commercial.
