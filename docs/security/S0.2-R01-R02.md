## Contrat d'identification

La cible est le paquet défini par `docker-compose.prod.yml`, construit et démarré sur le runner CI à partir du checkout. La configuration Compose résolue est lue en mémoire, sans publication de ses valeurs d'environnement, chemins de secrets ou paramètres de client.

| Image finale | Construction / référence | Correspondance au commit | Identité mesurée |
|---|---|---|---|
| PHP et rôles migrator/scheduler/maintenance | cible `php` de `docker/prod/Dockerfile`, base PHP 8.5.12-fpm-trixie ; alias `ikoma-php:<version>` | label OCI revision = SHA complet du checkout, source fixe ; refus de construire depuis des fichiers suivis modifiés ou des sources non suivies dans les chemins copiés | image ID SHA-256 de configuration Docker ; RepoDigests disponibles ou absence explicitée ; version PHP exécutée sans réseau/volume/secret |
| PostgreSQL | `postgres:18.6-trixie`, sans nouvelle variante ni nouvelle version | référence tiers résolue par le Compose du commit ; ne pas attribuer le code PostgreSQL au commit applicatif | image ID et digest de registre obligatoire ; version postgres mesurée |
| Nginx | cible `nginx`, base nginxinc/nginx-unprivileged:stable-alpine-slim | labels source/revision comme PHP | image ID et RepoDigests ou absence explicitée ; version nginx mesurée |

Pour chaque service `php`, `db`, `nginx`, l'ID de l'image configurée doit être identique à l'ID du conteneur réellement démarré en recette. L'analyse utilise cet ID immuable, **jamais le tag seul**. Les références configurées des trois rôles PHP supplémentaires doivent désigner la même image que PHP.

Un image ID est le digest de la configuration Docker. Ce n'est pas un digest de manifeste OCI de registre. Les images PHP/Nginx construites localement peuvent n'avoir aucun RepoDigest : le manifeste l'indique explicitement. Aucun digest de registre n'est fabriqué ; aucune image n'est poussée pour en obtenir un. Le digest tiers PostgreSQL est exigé puisqu'il est récupéré d'un registre. La publication d'une release et son verrou de déploiement appartiennent à une étape ultérieure autorisée.

Les labels relient la construction contrôlée à Git, mais ne constituent pas une attestation cryptographique indépendante. Les builds APT/bases mobiles ne deviennent pas reproductibles octet pour octet par l'ajout d'un label. Les versions de composants et les `FROM` sont inchangés.

## Contrat du contrôle R02

`scripts/security/final-images.py` n'utilise que Python standard, Docker et Trivy 0.76.1 déjà présents dans le dispositif. Il n'installe ni ne remplace d'outil. La CI exécute :

```sh
python3 scripts/security/final-images.py scan --output security-production
python3 scripts/security/final-images.py verify --output security-production
```

La deuxième commande est une étape CI distincte, également exécutée après l'échec de la première. Elle relit les preuves, vérifie leurs empreintes, leur identité, la présence des trois rapports et le seuil de décision. Elle refuse un rapport supprimé ou modifié après la collecte.

1. Initialiser un manifeste en état d'échec dans un dossier de preuves neuf. Refuser un dossier non vide afin qu'un rapport ancien ne masque jamais une analyse absente.
2. Vérifier le SHA source, la propreté des fichiers suivis, les empreintes Compose/Dockerfile/verrous et le SHA de checkout annoncé par Actions lorsqu'il existe.
3. Résoudre les trois images finales et leur identité runtime ; vérifier les labels PHP/Nginx et le digest tiers DB. Relever uniquement des champs autorisés, jamais un inspect/config complet dans une preuve publique.
4. Télécharger une seule base Trivy par collecte, en conserver le SHA-256 et les métadonnées datées. Refuser une base ou ses métadonnées manquantes. Utiliser cette même base pour les trois scans (`--skip-db-update`).
5. Exécuter Trivy sur les ID locaux avec `--image-src docker`, analyse vulnérabilités de toutes gravités, sans ignorance des non corrigées. Utiliser un fichier de configuration vide et une liste d'exclusion vide explicites ; retirer les variables héritées `TRIVY_*` du processus. Un scan ne doit pas substituer une autre image téléchargée depuis un registre.
6. Vérifier le JSON : schéma, version Trivy, type image, ID exact, OS reconnu et résultat de couverture des paquets OS. Un rapport vide `{}` ou une liste sans analyse OS ne vaut pas un résultat sans alerte.
7. Conserver les constats et gravités sans filtrer HIGH/CRITICAL selon l'existence d'un correctif. Continuer la collecte des autres services si l'un échoue, puis échouer globalement.

| Code de sortie | Sens | Effet CI |
|---|---|---|
| 0 | preuves complètes ; aucune HIGH/CRITICAL | contrôle réussi, sans promesse de sécurité globale |
| 1 | au moins une HIGH/CRITICAL, même sans correctif disponible | contrôle bloquant rouge attendu |
| 2 | outil indisponible, délai, image/conteneur manquant, divergence d'identité, métadonnées/rapport absent ou invalide | contrôle bloquant rouge technique, distinct d'une alerte de vulnérabilité |

Trivy utilise ici `--exit-code 0` pour produire le rapport de toutes gravités : **seul le résultat technique du scanner est alors attendu à zéro**. Le contrôleur calcule lui-même HIGH/CRITICAL sur le JSON validé et retourne 1. Les tests prouvent ce blocage avec des vulnérabilités sans `FixedVersion`. Il n'existe aucun `|| true` sur le scan ni sur le verdict final. Le scan bloquant de développement d'origine conserve ses commandes et son seuil ; seul son intitulé est corrigé.

## Preuves, confidentialité et limites

L'artefact `analyses-images-finales` est publié avec `if: always()` et absence de fichier bloquante. Rétention : 90 jours. Il contient `manifest.json` et les trois rapports `image-php.json`, `image-db.json`, `image-nginx.json` lorsqu'ils ont pu être produits. Un manifeste partiel porte un état d'erreur ; sa publication ne transforme pas le contrôle en succès.

Chaque entrée relie source, référence Compose, ID, RepoDigests, architecture, OS, version runtime, verdict et empreintes des rapports brut/expurgé. Les IDs du run et de sa tentative sont présents en CI. Le manifeste porte les versions et métadonnées de la base de vulnérabilités. Les rapports expurgés conservent paquets, versions, CVE, gravités et références ; ils omettent la configuration d'image, historique, variables d'environnement et les autres sections non nécessaires. Le brut reste dans un dossier temporaire privé et est détruit après collecte. Les stderr de Docker/Trivy ne sont pas publiés : les erreurs utilisent des codes stables.

Les labels ne prouvent pas le commit réellement servi sur un serveur client. Aucun serveur réel, registre de livraison ou base client n'est interrogé. La recette CI n'est pas un déploiement client. Une CI verte ne garantit pas que les règles de protection GitHub ou une automatisation externe empêchent un déploiement : ce verrou extérieur reste à vérifier dans un lot dédié. Une CI rouge produisant HIGH/CRITICAL est attendue dans R01–R02, puisque les composants restent inchangés.

Le hash de la base et ses dates identifient la base utilisée ; son fichier binaire n'est pas archivé dans cette phase. Cela ne garantit pas un rejeu historique octet pour octet après évolution du flux d'avis. Le contrôle reste réexécutable sur un même ID d'image avec une base fraîche, en conservant les nouvelles identités et les différences de résultats. La conservation des binaires de release et des bases historiques relève du contrat de conservation R09, pas d'une garantie inventée par R02.

Les exceptions ZAP/Gitleaks et les seuils Composer/npm existants ne sont ni élargis ni modifiés. Les anciens artefacts E2E peuvent nécessiter une revue distincte de l'expurgation des valeurs de recette ; aucune valeur n'est recopiée ici. Ce lot ne prétend pas résoudre R10.

## Vérification

Les tests de `tests/security/test_final_images.py` simulent les exécutables Docker/Trivy, leurs erreurs et leurs rapports. Ils n'utilisent aucun serveur. Ils couvrent les trois services, le lien commit/image, une base indisponible, un scanner défaillant, un rapport absent/invalide/d'une autre image, les rapports obsolètes, les suppressions/altérations de preuves, les HIGH/CRITICAL sans correctif, et l'absence de données privées dans les fichiers publiables.

Les preuves d'exécution réelle sur images finales doivent être lues dans le run de la PR et l'artefact associé. Sans ces preuves, seuls les tests du contrôleur sont démontrés. Les résultats et SHA précis sont consignés à la restitution de la PR, sans assimiler une simulation à un scan réel.
