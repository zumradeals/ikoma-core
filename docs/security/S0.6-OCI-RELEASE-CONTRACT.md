# S0.6 — Publication contrôlée de la candidate PostgreSQL par manifeste OCI

**État : conception et qualification Git seulement. Publication de candidat MANUELLE, non exécutée. Aucune migration ni déploiement autorisés.**

## Vision

Les images S0.4 (reconstruction bit à bit) et S0.5 (transport d'archive sur runner indépendant) sont qualifiées. L'archive temporaire S0.5 n'est pas une image distribuée à long terme et son SHA-256 ne constitue pas un digest de manifeste de registre OCI.

S0.6 prépare une publication **de candidat uniquement** dans GitHub Container Registry (GHCR), infrastructure du dépôt GitHub déjà utilisé, sans introduire un fournisseur externe. Elle n'autorise ni une installation chez un client ni un remplacement implicite de PostgreSQL en exploitation.

## Contrats

- **Vérité Git** : seuls `main` et le verrou `docs/security/S0.4-IMAGE-LOCK.json` définissent les parents Go/PostgreSQL, la révision officielle `gosu` et son empreinte.
- **Publication fermée par défaut** : le workflow `qualification-s06-ghcr.yml` réagit aux PR **uniquement pour les tests sans privilège**. La publication GHCR exige un événement **workflow_dispatch**, un SHA complet égal au commit `main` réellement extrait et le texte de confirmation `RELEASE_CANDIDATE_ONLY`. Le workflow doit exister sur `main` avant que cette action soit possible.
- **Pas de tag flottant** : publication exclusive sous `ghcr.io/zumradeals/ikoma-access-postgres-candidate:rc-<commit Git complet>`, avec refus de réutiliser ce tag s'il existe. Ni `latest` ni `stable` ni tag officiel `postgres`.
- **Sécurité de construction** : reconstruire depuis les deux digests parents Git, sans cache, pour `linux/amd64` seulement. Compiler `gosu` sans modification de source. Extraire le binaire, vérifier son SHA et sa provenance.
- **Trivy obligatoire** : scanner l'ID exact de l'image avant toute publication et bloquer à la moindre HIGH/CRITICAL ou à la perte de couverture de l'OS Alpine.
- **Attestation** : publier une attestation GitHub signée, attachée au **digest de manifeste du registre**, avec `actions/attest@v4` et OIDC GitHub ; le runner indépendant exige ensuite `gh attestation verify` au digest du candidat réellement publié. Permissions `packages:write`, `attestations:write` et `id-token:write` accordées **uniquement au job de publication manuel**. Référence : [documentation GitHub de la provenance des images](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations).
- **Vérification par un autre runner** : authentification GHCR, `docker pull <image>@sha256:<digest-du-manifeste>`, vérification que le digest de registre est présent dans `RepoDigests`, nouveau scan Trivy de l'image chargée, provenance du `gosu` et jeu relationnel fictif **1 000 visiteurs / 1 000 badges / 2 000 passages** sur un volume jetable.
- **Échec bloquant** : aucune tolérance implicite sur un scan, une attestation manquante, un digest discordant, une image déjà publiée, une base ne démarrant pas, une provenance inexacte ou des données fictives incomplètes.
- **Identités non substituables** : un SHA-256 d'archive `.tar`, un ID de configuration Docker, un identifiant d'index OCI, un digest de manifeste dans GHCR et le SHA-256 du binaire `gosu` sont des valeurs différentes. Ne jamais les interchanger.

## Conception / publication / exploitation : frontières

| Étape | Possible dans cette PR | Autorise production ? |
|---|---|---|
| Tests des contrats S0.6 en PR | Oui, sans droits de publication | Non |
| Fusion de la chaîne de qualification Git | Seulement après décision explicite | Non |
| Publication candidate GHCR sur `main` | Événement manuel, confirmation et commit exacts | Non |
| Réimport depuis le digest, Trivy, attestation, PostgreSQL fictif | Obligatoire après publication | Non |
| Bascule de `docker-compose.prod.yml`, modification de volumes ou migration | **Hors périmètre** | **Non** |

La publication de candidate peut créer une ressource GHCR portant les binaires distribuables et des attestations. Le contrôle d'accès et la visibilité du package doivent être revus par les responsables avant la première exécution. Une publication GHCR est durable tant que l'organisation maintient le package, mais la **pérennité et l'immutabilité administrative** exigent aussi une politique de rétention, de droits et d'interdiction de suppression/réécriture du registre.

## Prérequis non réalisés

1. Mainteneur identifié, responsable sécurité, exploitant et approbateur de migration.
2. Politique de mise à jour Go/PostgreSQL/Alpine, délai de traitement des CVE, contrôle des permissions GHCR, politique de rétention du package.
3. Copie représentative, isolée et autorisée de la base existante **ou constat officiel d'une installation vierge**.
4. Sauvegarde chiffrée vérifiée, fenêtre de gel des écritures, plan de réconciliation, objectifs RPO/RTO et retour arrière testé sur l'installation concernée.
5. Diff dédié permettant la substitution explicite de la référence PostgreSQL de production par **digest OCI vérifié**, avec validation de l'environnement et GO distinct ; ne jamais utiliser le même volume physique Debian comme volume Alpine.

## Résultat attendu et décision

**GO préparation et tests statiques du workflow.** Le passage à une publication candidate GHCR exige une validation explicite du package et un déclenchement manuel. **STOP pour toute mise en production, transfert de données client, migration, modification de Compose et suppression des contrôles Trivy.**
