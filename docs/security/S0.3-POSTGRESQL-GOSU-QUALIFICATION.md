# S0.3-B — PostgreSQL : revue Go/gosu et répétition d'une restauration Debian → Alpine

**État : qualification sur données fictives, sans changement de base livrée.**
Base Git : `1cb59cde719d7cc29b16914826b35117881d3514` (PR #49). Le lot PHP est indépendant (PR #52).

## Vision — supprimer le blocage sans risque sur les données
Le scan de l'image PostgreSQL Debian finale a détecté 88 occurrences HIGH/CRITICAL dans la CI précédente, dont la critique libxml2 `CVE-2026-6653`. La qualification PostgreSQL Alpine précédente présente **25 HIGH + 1 CRITICAL** liées au binaire Go `gosu` 1.19, assemblé avec Go 1.24.6. La revue `govulncheck` avait identifié zéro symbole affecté pour une CVE ciblée ; ce constat limité ne vaut pas exemption générale.

Le dépôt upstream `tianon/gosu` distribue encore 1.19, avec Go 1.24.6, lors de cette revue ; ne pas appeler une réinstallation du même binaire « correctif ». Vérifier à chaque nouveau scan le **binaire et le digest réellement exécutés**.

## Conception — contrats non négociables
1. L'image réellement livrée reste `postgres:18.6-trixie` jusqu'à nouvelle décision ; ne modifier ni `docker-compose.prod.yml`, ni `docker-compose.yml`, ni les volumes PostgreSQL.
2. La candidate exploratoire `postgres:18.6-alpine3.24` est construite uniquement dans la CI et reçoit les mises à jour `apk` officielles.
3. Relever image-ID, identité du binaire `gosu`, CVE HIGH/CRITICAL, liens `govulncheck`, cas sans avis correspondant ; chaque inconnue reste « examen requis ».
4. Exécuter une restauration logique **d'un conteneur Debian fictif vers un conteneur Alpine neuf**, sans réutilisation de répertoire de données. Comparer les noms accentués, index, `pg_trgm`, `unaccent` et l'ordre explicite `COLLATE "C"`.
5. Préserver les portes Trivy actuelles. Un résultat de test fonctionnel vert ne signifie pas GO de sécurité ou de migration réelle.
6. Interdire toute création de données client, accès à un serveur réel, publication d'une clé ou d'un dump de production.

## Implémentation de qualification
- `scripts/security/s03-pg-migration-fixture.sql` contient des données strictement fictives.
- `.github/workflows/qualification-postgresql-s03.yml` crée deux conteneurs jetables, sauvegarde/restaure les données fictives, compare les requêtes, inspecte les paquets et conserve une preuve Trivy liées aux identités d'images.
- `scripts/security/s03-pg-scan-gate.py` refuse l'image candidate si des HIGH/CRITICAL subsistent, même si elles ont déjà été documentées. Aucun fichier d'ignorance ni exception tacite.
- Le rapport d'atteignabilité `scripts/security/audit-gosu-highs.py` de S0.2 est conservé comme source du diagnostic par CVE, et doit être réexécuté avec le binaire exact avant décision.

## Décision et retour arrière
**GO pour expérimenter**, pas GO pour remplacer la base actuelle. Une adoption future nécessite zéro vulnérabilité bloquante ou décision formelle sur les risques résiduels, procédure opérateur sauvegarde/restauration et reprise sur **copie représentative**, contrôle de cohérence, REINDEX si nécessaire, tests métier et observation post-migration. Aucun `docker compose up` de production n'est autorisé par ce lot.

Il n'y a **pas de retour arrière de données** à réaliser après ce lot documentaire/CI, car aucune base existante n'est modifiée. La PR reste DRAFT jusqu'au dossier de décision.
