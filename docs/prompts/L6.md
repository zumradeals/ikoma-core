Vérifie leurs versions stables actuelles et documente les choix dans docs/JOURNAL_DECISIONS.md.

OBJECTIF
Rendre le poste d'accueil pleinement utilisable sans réseau, sans perte ni doublon à la reconnexion, avec des données personnelles protégées sur la tablette.

À FAIRE
1. Enrôlement des appareils (Administration > Postes, permission postes.gerer, créée au lot L3b) : création d'un poste, code d'enrôlement à usage unique, échange contre un jeton d'appareil (stocké haché dans devices.token_hash), révocation immédiate, date de dernière synchronisation visible. Un appareil non enrôlé ne peut ni se connecter au poste ni synchroniser.
2. Implémentation locale de PosteRepository (IndexedDB) : au démarrage en ligne, copie sur la tablette la liste des visiteurs de l'événement, les catégories, les zones, les hôtes et les badges réservés au poste, avec un numéro de version de liste. La recherche locale est tolérante aux accents, aux fautes et trouve sur n'importe quel mot du nom, avec des résultats identiques à ceux du serveur sur les cas de test de L5.
3. Chiffrement local : toutes les données personnelles conservées sur la tablette (liste, file d'opérations, photos en attente) sont chiffrées (WebCrypto, AES-GCM) avec une clé dérivée du code PIN et d'un secret d'appareil, selon docs/AUTH_HORS_LIGNE.md. Effacement local après le nombre d'échecs de PIN fixé, à la révocation, à la déconnexion explicite et à la fin de l'événement.
4. Authentification hors ligne selon le document validé : déverrouillage par PIN, verrouillage automatique après inactivité (durée dans settings), limites d'actions hors ligne.
5. File d'opérations : chaque action (recherche exclue) crée une opération horodatée, avec son identifiant unique, dans une file locale persistante, rejouée dans l'ordre à la reconnexion vers POST /poste/api/sync (authentifié par le jeton d'appareil et l'agent). Traitement idempotent côté serveur grâce à sync_operations. Reprise sûre après coupure en plein envoi.
6. Règles de conflit côté serveur : jamais d'écrasement silencieux. Badge déjà associé, badge réservé à un autre poste, visiteur déjà entré, agent désactivé entre-temps, fiche modifiée entre-temps : l'opération est marquée « conflit » avec sa raison, mise en quarantaine, journalisée, et signalée au superviseur (table alerts créée au lot L8 : crée dès maintenant une table sync_conflicts consultable, que L8 affichera). Les autres opérations de la file continuent d'être traitées.
7. Heures : conserve l'heure de la tablette et l'heure de réception serveur ; signale tout écart supérieur à un seuil (réglage) ; les horodatages d'audit utilisent l'heure serveur et l'heure déclarée.
8. Service worker : met en cache uniquement les fichiers de l'application (JS, CSS, polices, manifeste), jamais de contenu authentifié ni de données ; la page du poste doit s'ouvrir sans réseau après une première visite ; mise à jour de l'application sans perte de la file locale (conserve le correctif PWA de L1).
9. Bandeau d'état du poste : réseau (en ligne / hors ligne), nombre d'opérations en attente, dernière synchronisation, conflits éventuels, avec des messages simples. Bouton « Synchroniser maintenant ». Indication claire quand la liste locale est périmée (version plus ancienne que celle du serveur) et mise à jour automatique au retour du réseau.
10. Journalisation (service Audit) : poste.enrole, poste.revoque, sync.recue, sync.conflit, poste.efface, avec identifiants et nombres uniquement.

CONTRAINTES
- Aucune donnée réelle. Aucun nom de personne dans les journaux ni les messages techniques.
- Le jeton d'appareil et le PIN ne sont jamais écrits dans les journaux ni conservés en clair.
- Aucun appel réseau sortant hors du serveur de l'application. Aucun contenu authentifié dans le cache du service worker.
- Ne supprime ni n'affaiblis aucun test existant. Ne modifie pas les droits du compte applicatif sur audit_logs, access_events et identity_checks.

CRITÈRES D'ACCEPTATION
- Parcours Playwright : réseau coupé pendant le traitement de 30 visiteurs, puis rétabli : toutes les opérations sont appliquées une seule fois, sans perte ni doublon ; compteurs exacts.
- Test de rejeu : la même file envoyée deux fois ne change rien. Test de coupure en plein envoi : reprise correcte.
- Test de conflit : deux postes hors ligne associent le même badge (hors lot réservé) ; une seule association est appliquée, l'autre est en conflit signalé, rien n'est écrasé.
- Tests Pest : appareil non enrôlé refusé, appareil révoqué refusé, agent désactivé en quarantaine, jeton jamais journalisé. Tests Vue / Playwright : chiffrement local (aucune donnée lisible dans IndexedDB), effacement après échecs de PIN, verrouillage après inactivité.
- Recherche locale : mêmes résultats que le serveur sur le jeu de cas de L5 ; temps de recherche local inférieur à 200 ms sur 5 000 fiches.
